# Email infrastructure — status & handoff

Snapshot for whoever picks this up next. Covers what is DONE (applied to Azure) and what
REMAINS. Companion to [infra/azure/README.md](../infra/azure/README.md) (how the Terraform
works) and [azure-email-setup.md](azure-email-setup.md) / [email-scanning-milestones.md](email-scanning-milestones.md)
(the feature plan).

## TL;DR

The mailbox-OAuth infrastructure is provisioned via Terraform and applied to production.
Email is **off**. To turn it on, an admin must place the Entra client secret in Key Vault
and the app deployment must set the `EMAIL_*` env vars — see "Remaining". The scanning
pipeline (Service Bus + worker + OpenAI) is written but not applied.

## Done (verified in Azure)

Infrastructure lives in two Terraform root modules under `infra/azure/`:
- `oauth/` — **APPLIED**. State key `email-infra.tfstate` in the `ileratfstate` account.
- `scanning/` — **written, NOT applied**. State key `email-scanning.tfstate`.

Applied by `oauth/` and confirmed:
- Key Vault `ilera-email-01a341d5` — RBAC-only, purge protection, soft-delete 90d.
- Fernet token-encryption key (`ilera-email-token-key`) — generated by Terraform, in the vault.
- RBAC: API managed identity (`8a17deab…`) = `Key Vault Secrets User` (read); CI SP
  (`9d46b02b…`, `ilera-deploy`) = `Key Vault Secrets Officer` (write the Fernet key).
- Key Vault audit diagnostics → Log Analytics workspace `ilera-email-logs`.
- Vault network ACL default action = `Allow` (RBAC still gates access; see note in Remaining).

CI/CD (`.github/workflows/terraform.yml`) is working end-to-end: plan on PR/push, apply on
`main` gated behind the `infra-production` GitHub Environment (manual approval). Proven with
a successful apply of `oauth/`.

Decisions made along the way (context for future changes):
- **Entra app is managed OUTSIDE Terraform.** Managing a directory object from the CI SP
  would need Microsoft Graph app-management permission + admin consent — rejected as too
  much standing privilege. Terraform only references `var.mailbox_client_id`. The app
  (`ilera-microsoft-mailbox`, client id `c3b57022…`) already exists.
- **Container app template is NOT written by Terraform.** A PUT drops the app's existing
  secrets (`ContainerAppSecretInvalid`). The app deploy pipeline owns env vars / secret refs.
- **Single Azure OpenAI** — reuse the existing account, no dedicated resource.
- **Role assignments use deterministic `uuidv5` names** matching the earlier setup's GUIDs,
  so imports are clean and re-applies never replace.
- **State is remote** in `ileratfstate` (TLS 1.2). No local state.

## Remaining

### A. Turn on mailbox connections (no scanning yet)

1. **Place the Entra client secret in Key Vault (admin, out of band).** The Entra app's
   client secret is not managed by Terraform. Create/rotate it (portal or
   `az ad app credential`) and write the VALUE into the vault:
   ```sh
   az keyvault secret set --vault-name ilera-email-01a341d5 \
     --name ilera-microsoft-client-secret --file <secret-file>   # --file, not --value
   ```
   Requires a data-plane role on the vault (Secrets Officer). The CI SP has it; a human
   needs it granted (RBAC-only vault).
2. **Set `EMAIL_*` env on the API via the app deployment** (NOT Terraform — see decision
   above). Values (all non-secret; the app reads the secret from the vault by managed
   identity):
   ```
   EMAIL_MICROSOFT_TENANT_ID          = 5c8a1e25-bdc4-4ced-b8c2-3cda51c721d9
   EMAIL_MICROSOFT_CLIENT_ID          = c3b57022-1fcd-4434-a04a-b9ce41e54987
   EMAIL_MICROSOFT_REDIRECT_URI       = https://ileracare.app/api/email/microsoft/callback
   EMAIL_KEY_VAULT_URL                = https://ilera-email-01a341d5.vault.azure.net
   EMAIL_MICROSOFT_CLIENT_SECRET_NAME = ilera-microsoft-client-secret
   EMAIL_TOKEN_ENCRYPTION_KEY_NAME    = ilera-email-token-key
   EMAIL_USE_MANAGED_IDENTITY         = true
   EMAIL_CONNECTIONS_ENABLED          = true   # the switch
   EMAIL_SCANNING_ENABLED             = false  # keep false until the pipeline is live
   ```
   `backend/app/config.py` has safe defaults, so the app runs today with these unset/false.
3. **Verify the Entra app registration** has: single-tenant (`AzureADMyOrg`), web redirect
   `…/api/email/microsoft/callback`, delegated Graph scopes `Mail.Read`, `openid`, `profile`,
   `offline_access`. Admin consent may be required by tenant policy.
4. **Callback logging:** ensure the proxy/ingress omits the query string on
   `/api/email/microsoft/callback` (it carries a short-lived auth code). Do not enable HTTP
   body logging for token/Key Vault requests.
5. **Live validation** (the milestone's completion criterion): connect a mailbox, then test
   refresh, disconnect/reconnect, ownership isolation (another account can't read/claim),
   and credential deletion.

### B. Apply the scanning pipeline (`infra/azure/scanning/`)

Prerequisites, then apply:
1. Build & push the scan worker image; set `scan_worker_image` in `scanning/terraform.tfvars`.
2. Set `existing_openai_account_name` and `email_openai_deployment_name` (the existing
   Azure OpenAI account + deployment to use for extraction).
3. `cd infra/azure/scanning && terraform init && terraform plan` — review — then apply
   (via the pipeline: `workflow_dispatch` with module=scanning, action=apply; or add
   `scanning` to the workflow's plan matrix).
4. Provisions: Service Bus (`ilera-email-bus`, queue `email.scan`, dedup + DLQ, no local
   auth), the worker Container App (`ilera-email-worker`, queue-scaled), and RBAC — API =
   Service Bus Sender, worker = Receiver + Secrets User + Cognitive Services OpenAI User.
5. **HIPAA for OpenAI:** confirm the OpenAI account is BAA-covered and has content-logging /
   abuse-monitoring **opted out** for PHI.
6. Implement the still-missing app code (per email-scanning-milestones.md §3–5): the Graph
   webhook/notification ingress, the worker's fetch+extract, and the Care Calendar event
   review UI. Only then flip `EMAIL_SCANNING_ENABLED=true`.

### C. Hardening / follow-ups (optional, not blocking)

- **Key Vault private endpoint + `default_action = Deny`.** Currently `Allow` because CI
  runs from dynamic GitHub-hosted IPs not covered by the `AzureServices` bypass, and a Deny
  default blocks CI's own secret writes. Once a VNet-integrated environment + private
  endpoint exist (and CI runs from a known network), set
  `var.key_vault_network_default_action = "Deny"`. RBAC already gates all access regardless.
- **Long-term audit retention.** Log Analytics interactive retention caps at 730 days.
  HIPAA-scale retention (e.g. 6 years) needs archive tier or continuous export to immutable
  storage — not yet configured.
- **Workflow weakness:** `apply` does not `needs:` the `plan` job, so a failed plan doesn't
  block the apply gate from appearing. Only approve an apply whose own run's plan succeeded.
  Consider adding `needs: plan` (with the scanning matrix caveat) to enforce this.
- **Client-secret rotation** is manual/out-of-band (see README → Rotation). Track its
  expiry and rotate before it lapses.
